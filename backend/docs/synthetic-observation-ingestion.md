# Secure synthetic observation ingestion — Phase 4C.3B

`POST /api/simulation/captures/{captureId}/observations` receives complete original
engine envelopes. It never fetches Python URLs. No Python sender, frontend connection,
scope provisioning route, medical rules, alert generation, or ML inference is included.

## Authorization and bounds

Use the existing NASA_OFFICER login session, CSRF token, and explicit development/demo
gate from [capture registration](simulation-capture-registration.md). Both
`ASTROHEALTH_ENV=development` (or `demo`) and
`SIMULATION_CAPTURE_REGISTRATION_ENABLED=true` are required. The flag defaults to false;
production is refused even with the flag. No environment setting was enabled by this
implementation. Do not pass officer credentials or session secrets to Python.

The service reloads and locks the enabled officer account, then locks that officer's
capture. An astronaut account cannot impersonate an officer by supplying authorities,
roles, destination UUIDs, or another officer's capture ID. CSRF remains required and
CORS origins/headers are unchanged. Missing/inaccessible captures return 404.

Requests require `Content-Type: application/json`. The endpoint reads at most 1 MiB
plus one sentinel byte, even without Content-Length. A batch contains 1–100 unique,
positive, strictly ascending export sequences; each canonical envelope is at most
64 KiB. Parsing rejects duplicate object keys, trailing JSON, nesting beyond 32 levels,
and oversized strings/numbers. Service transactions have a 30-second timeout.

## Request and response

Use the Python `astrohealth.simulation.export.v1` wrapper and original `items` objects:

```http
POST /api/simulation/captures/<registered-capture-UUID>/observations
Content-Type: application/json
Cookie: JSESSIONID=<existing-officer-session>
X-CSRF-TOKEN: <fresh-token>
```

A complete, original-engine example is in
[examples/simulation-ingestion-request.json](examples/simulation-ingestion-request.json).
Its workspace is illustrative; register the actual workspace/run/profile manifest and
use the resulting capture ID. The minimal wrapper is:

```json
{
  "schema_version": "astrohealth.simulation.export.v1",
  "synthetic": true,
  "workspace_id": "42c3c89a-0ef3-495e-962a-1c4397a93b01",
  "items": [{"sequence": 1, "envelope": "<complete object in linked example>"}]
}
```

The string above abbreviates the envelope; an actual request must contain the full
object, including values, metrics, scope descriptor, provenance, simulation metadata,
baseline snapshots and deviations. Chart points and `/api/state` projections are refused.
Known export pagination fields are accepted but are not used as measurement content,
proof of delivery, or URLs to fetch. Unknown wrapper/envelope/subtype fields are refused.
An export containing multiple runs must be partitioned into the correct capture/run
batches; unapproved source profiles are never silently skipped.

Successful first ingestion returns 200:

```json
{
  "captureId": "3414095a-b67b-4d36-b21a-ea4cb37c2967",
  "created": 1,
  "duplicates": 0,
  "results": [{
    "sequence": 1,
    "sourceRecordId": "194acf81-06d0-535c-8e0f-3f8791704f2f",
    "observationId": "b04d75b5-a1a5-46f9-bcb0-24bdd3253841",
    "duplicate": false
  }]
}
```

Response IDs are illustrative; the observation UUID is generated by PostgreSQL. A retry
returns the original observation UUID with `created: 0`, `duplicates: 1`, `duplicate: true`.
There is no partial-success response: one invalid/conflicting/missing-scope record rolls
back every new header, value, and receipt in that batch. Existing committed results remain.

## Identity, values and provenance

The wrapper workspace and each envelope's run UUID must match the capture. The source
UUID/crew-code pair must match its immutable approved mapping. Only the server-resolved
backend astronaut UUID is inserted; mission/check-in/scope UUID assertions are refused
(the exported placeholders must be null). Destination `crew-01`–`crew-04` profiles must
still exist and be active; ingestion never creates them or their login accounts.

Schema version, synthetic/source flags, engine version and seed are checked against the
registered run. Indicator/storage kind/table, metric names, units, supported activity
contexts, subtype shape and metric/value agreement are validated against explicit engine
v1 vocabulary and database catalogs. `value_table` is compared to an allowlist and never
interpolated as a SQL identifier. Noncanonical units are rejected; no conversion is guessed.

All headers go to `health_observations`; values map as follows:

| Family / metric | Value table | Canonical unit |
| --- | --- | --- |
| Heart rate | `health_measurements` | beats/min |
| Blood glucose (`blood_sugar`) | `health_measurements` | mmol/L |
| Body temperature | `health_measurements` | Cel |
| Cumulative absorbed radiation dose | `health_measurements` | mGy |
| Paired systolic/diastolic blood pressure | `blood_pressure_observations` | mmHg |
| Completed sleep | `sleep_sessions` | elapsed/asleep seconds; catalog duration h |
| Numeric demonstration mood | `mood_assessments` | score on approved synthetic scale |
| Grip strength / muscle mass | two separate `muscle_assessments` rows/observations | kgf / kg |
| Areal bone mineral density | `bone_density_examinations` | g/cm2 |

Sleep end must equal measured_at, with nonnegative asleep seconds within the completed
session. NUMERIC capacity and SQL sign/scale constraints are checked. Values are rounded
explicitly HALF_UP to SQL column scales (scalar 6, pressure 3, mood/muscle 4, bone 6);
radiation must already be exactly representable at scale 6. Raw envelope numbers remain
available unchanged in provenance. The mood scale 1–5 and named synthetic methods come
from the existing engine/scope contract, not a clinical threshold policy.

Measurement timestamps retain the original instant, require an offset, microsecond
precision or coarser, and years 0001–9999. Measurements may not precede the registered
run's start. Future virtual timestamps are allowed: accelerated simulations do not use
server wall time as measurement time. Database ingestion time remains separate.

Header provenance retains the original engine provenance and the complete original
envelope, explicitly marked `demonstration_only`. Original baseline/deviation snapshots
remain JSON provenance and are never inserted into `personal_baselines` or
`monitoring_rules`. Simulation metadata retains engine controls/tick/context and adds
server capture/workspace/source identity. Mood additionally records
`SYNTHETIC_DEMONSTRATION_NOT_ASTRONAUT_SUBMISSION` and fixed demonstration-only notes.

## Approved scopes and unresolved provisioning

Generic metrics require the five existing V22 `default` definitions. Specialized scope
identity and every site/protocol/version/scale/origin dimension must exactly match the
expected engine contract and an existing immutable database definition. The service
does not silently alias, weaken or create a definition. A missing definition returns:

```json
{
  "error": "missing_scope",
  "message": "An approved comparison scope is required before ingestion.",
  "requiredScope": {
    "indicator_code": "mood", "storage_kind": "MOOD",
    "scope_code": "simulation-mood-v1", "scale_name": "SYNTHETIC_DEMO_MOOD",
    "scale_version": "1", "scale_min": 1, "scale_max": 5
  }
}
```

Status is 422. Required scope metadata is disclosed only after creator authorization and
approved profile resolution. A conflicting existing definition returns 409
`scope_definition_conflict`; immutable scopes cannot be repaired by this endpoint.

Before live integration, trusted administrators must separately approve/provision:

- `simulation-mood-v1` with the named synthetic scale;
- `simulation-grip_strength-v1` and `simulation-muscle_mass-v1` with their separate sites/methods;
- `simulation-bone-v1` with its site/protocol;
- a personal radiation origin for each capture/destination, using the exact descriptor
  returned by `missing_scope`.

No admin provisioning operation was executed. The development database may also lack
the required astronaut profiles and officer account. Registration/ingestion fail explicitly
until those separately authorized prerequisites exist. Python delivery/checkpoint handling
remains an integration blocker, not a reason to bypass validation. Phase 4C.4 provides
an [explicit authenticated scope command](demo-simulation-scope-provisioning.md) and
V32 approval audit infrastructure; neither migration nor provisioning has been run
against the development database. The ingestion resolver still never creates scopes.

## Radiation, lifecycle and receipts

The exported radiation descriptor carries the fictional source UUID/run origin. It is
verified, then resolved to server scope code
`simulation-capture-<captureUUID>-<backendAstronautUUID>` with the real destination owner,
WHOLE_BODY, the registered accumulation start, and SYNTHETIC_DEMO_ABSORBED_DOSE. A new
workspace or independent capture therefore needs a separate approved origin. mGy is
absorbed dose; no mSv/environmental-dose interpretation is allowed.

Scope/destination locks serialize accumulation checks. New radiation measurements must
be strictly later than the last stored measurement in that origin and nondecreasing in
value, independent of activity context. Equal-time new identities, older measurements,
decreases, and measurements before origin are rejected. Exact receipt retries return the
original result before accumulation checks, so they do not advance or reset dose.

New records require ACTIVE. Close and ingestion share the capture lock. CLOSED captures
accept only exact, already committed receipt retries, including their original result IDs;
any new record rejects the entire batch. Destinations must still be active for retries.

V31 UNIQUE constraints on `(capture_id, source_record_id)`, `(capture_id, export_sequence)`
and observation ID remain final idempotency safeguards. Account/capture locks serialize
concurrent first inserts; receipt inspection happens before insertion, not by catching a
unique violation inside an already aborted PostgreSQL transaction. V25's deferred
completeness trigger is checked before returning; header/subtype/receipt writes commit
in the same transaction. There is no reservation/partial receipt state.

Hashes use version `astrohealth.simulation.canonical.v1`: UTF-8 SHA-256 over the version,
capture UUID, workspace UUID, mapping UUID and base-10 sequence, each followed by LF,
then canonical JSON of the entire original envelope. Object keys sort by Java UTF-16
lexicographic order; arrays retain order; strings retain Unicode content with JSON quoting;
booleans/null retain their JSON tokens. Numbers parse as exact decimals, remove trailing
zeros, normalize signed zero to `0`, and expand exponents to plain decimal. Exponent
expansion is bounded to 128 places. This is a custom versioned format, not a claim of
RFC 8785 compliance. HTTP whitespace/key order/number spelling and page counters do not
change identity. Changed original content, mapping or sequence with the same source
identity returns 409 `receipt_conflict`; historical records are never overwritten.

Other fixed errors include 400 `invalid_observation`, 403 `unapproved_profile`,
409 `astronaut_archived`, `capture_not_active` or `radiation_order_conflict`, and 413
`payload_too_large`/`observation_too_large`. Existing authentication/CSRF errors retain
their 401/403 conventions. Storage unavailability returns 503. No error includes SQL,
raw measurement payloads, credentials or session secrets.

## Safe verification

Tests use isolated PostgreSQL 17 Testcontainers, with per-test schemas for committed,
rollback, and concurrency fixtures. The checked-in engine fixture contains 13 unmodified
envelopes selected from a deterministic 28-day run with default fictional configuration,
covering all nine families and both muscle metrics. No Python API process is started.
Specialized scopes are inserted only as disposable test fixtures.

```powershell
.\mvnw.cmd -B '-Dtest=SimulationIngestionTests,SimulationIngestionConcurrencyTests,SimulationCaptureRegistrationTests,SimulationCaptureDisabledTests,SimulationCaptureProductionGateTests,SimulationPersistenceTests' test
.\mvnw.cmd -B test
```

No development database migration, real provisioning, clinical threshold/baseline
configuration, Python sender, alert generation or trained-model execution is authorized
by these test commands. Stop for review before connecting Python delivery.
